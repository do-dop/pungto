# Pungto 일정 관리 기능 요구사항 검증표

## 1. 검증 목적

본 문서는 Pungto 실시간 일정 관리 기능 요구사항이 구현 전에 충분히 명확하고 검증 가능한지 확인하기 위해 작성하였다.

초기 Pungto 개발에서는 요구사항 분석 없이 생성형 AI를 활용해 기능을 먼저 구현했기 때문에, 화면은 존재하지만 실제 기능으로 완성되지 않은 항목이 발생하였다. 이번 개선에서는 요구사항의 품질을 먼저 검토하여 구현과 테스트의 기준으로 활용한다.

---

## 2. 요구사항 품질 기준

요구사항은 다음 기준에 따라 검토한다.

| 기준 | 의미 |
|---|---|
| 원자성 | 하나의 요구사항이 하나의 기능 또는 조건만 다루는가 |
| 완전성 | 기능 수행에 필요한 조건과 예외가 빠지지 않았는가 |
| 비모호성 | 해석이 여러 가지로 갈릴 수 있는 표현이 없는가 |
| 일관성 | 요구사항 사이에 서로 충돌하는 내용이 없는가 |
| 추적성 | 요구사항이 사용자 스토리, 설계, 테스트로 연결될 수 있는가 |
| 우선순위화 | 필수 요구와 선택 요구가 구분되어 있는가 |
| 테스트 가능성 | 실제 테스트 케이스로 검증할 수 있는가 |

## 4. 보완한 요구사항

### 4.1 실시간 변경 반영 요구사항 보완

초기 표현:

> 시스템은 일정 변경 내용을 실시간으로 반영해야 한다.

문제점:

- 실시간의 기준이 모호하다.
- 누구의 화면에 반영되어야 하는지 불명확하다.
- 테스트 방법이 구체적이지 않다.

보완 후 표현:

> 시스템은 같은 room ID를 가진 방에 접속한 다른 사용자의 화면에 일정 생성, 수정, 삭제 결과를 새로고침 없이 반영해야 한다. 이 요구사항은 두 개의 브라우저 또는 두 개의 세션을 사용하여 검증한다.

### 4.2 삭제 요구사항 보완

초기에는 일정 삭제 기능만 정의했지만, 실수로 인한 삭제를 방지하기 위해 삭제 확인 절차를 권장 요구사항으로 추가하였다.

## 5. 요구사항 검증 결과 요약

요구사항 검증 결과, 대부분의 요구사항은 기능 단위로 원자적으로 작성되었고 테스트 케이스로 연결 가능하였다.

다만 실시간 반영 요구사항은 처음에는 표현이 모호하여 보완이 필요했다. 이를 두 브라우저 또는 두 세션에서 확인하는 방식으로 구체화하여 테스트 가능성을 높였다.

이번 검증을 통해 일정 기능의 완료 기준이 단순히 화면 표시가 아니라, 데이터 저장, 방별 분리, 실시간 반영, 입력 검증, 기존 기능 회귀 테스트까지 포함해야 함을 명확히 하였다.

---

## 6. 프로세스 적용의 교훈

초기 Pungto 개발에서는 생성형 AI에게 포괄적으로 협업 서비스를 구현하도록 요청했기 때문에, 일정 기능처럼 화면은 존재하지만 실제 기능으로 완성되지 않은 항목이 발생하였다.

요구사항 검증 절차를 적용하면서 각 기능이 어떤 조건을 만족해야 완료되는지 명확해졌고, 구현 전에 테스트 기준을 함께 고려할 수 있었다.

이를 통해 바이브코딩에서도 요구사항의 원자성, 완전성, 비모호성, 테스트 가능성을 먼저 점검해야 AI가 생성한 결과물을 올바르게 평가할 수 있다는 점을 확인하였다.
