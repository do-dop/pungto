# Pungto 일정 관리 기능 테스트 계획서

## 1. 테스트 목적

본 문서는 Pungto 일정 관리 기능 개선 결과가 요구사항을 만족하는지 검증하기 위해 작성하였다.

초기 Pungto 개발에서는 화면에서 기능이 보이는지 중심으로 확인했기 때문에, 실제 데이터 저장, 실시간 동기화, 예외 처리, 기존 기능 회귀 여부를 체계적으로 검증하기 어려웠다.

이번 개선에서는 구현 전에 테스트 계획을 먼저 작성하여, AI가 생성한 코드가 요구사항과 품질 기준을 만족하는지 확인하는 기준으로 활용한다.

---

## 2. 테스트 범위

### 포함 범위

- 일정 목록 조회
- 일정 생성
- 일정 수정
- 일정 삭제
- 빈 제목 입력 검증
- 빈 날짜 입력 검증
- room ID 기반 데이터 분리
- Supabase Realtime 기반 실시간 반영
- 기존 채팅 기능 회귀 테스트
- 기존 칸반 기능 회귀 테스트
- lint 및 build 확인

### 제외 범위

- 반복 일정
- 알림 발송
- 외부 캘린더 연동
- 로그인 기반 권한 테스트
- 대규모 부하 테스트

## 3. 테스트 전략

| 테스트 유형 | 적용 내용 |
|---|---|
| 기능 테스트 | 일정 조회, 생성, 수정, 삭제가 요구사항대로 동작하는지 확인 |
| 예외 테스트 | 빈 제목, 빈 날짜, 저장 실패 상황을 확인 |
| 통합 테스트 | UI, hook, Supabase 저장소, Realtime 이벤트가 연결되는지 확인 |
| 상태 기반 테스트 | 일정 생성 전후, 수정 전후, 삭제 전후의 상태 변화를 확인 |
| 회귀 테스트 | 일정 기능 추가 후 기존 채팅과 칸반 기능이 정상 동작하는지 확인 |
| 인수 테스트 | 요구 명세서의 인수 조건을 모두 만족하는지 확인 |

## 5. 테스트 케이스

| TC ID | 관련 요구사항 | 테스트 유형 | 수행 절차 | 기대 결과 |
|---|---|---|---|---|
| TC-01 | FR-01 | 기능 | 일정 메뉴에 진입한다. | 현재 방의 일정 목록이 표시된다. |
| TC-02 | FR-02, FR-05 | 기능 | 제목, 날짜, 설명을 입력하고 저장한다. | 새 일정이 현재 방 일정 목록에 표시된다. |
| TC-03 | FR-03 | 기능 | 기존 일정의 제목 또는 날짜를 수정한다. | 수정된 내용이 목록에 반영된다. |
| TC-04 | FR-04, FR-07 | 기능 | 일정 삭제 버튼을 누르고 삭제를 확인한다. | 일정이 목록에서 제거된다. |
| TC-05 | NFR-01 | 예외 | 제목을 비우고 저장한다. | 저장되지 않고 제목 입력 안내가 표시된다. |
| TC-06 | NFR-02 | 예외 | 날짜를 비우고 저장한다. | 저장되지 않고 날짜 입력 안내가 표시된다. |
| TC-07 | FR-05, NFR-03 | 통합 | A방과 B방에 서로 다른 일정을 생성한다. | 각 방에는 자신의 일정만 표시된다. |
| TC-08 | FR-06 | 실시간 | 브라우저 A에서 일정을 생성한다. | 브라우저 B에 새 일정이 새로고침 없이 표시된다. |
| TC-09 | FR-06 | 실시간 | 브라우저 A에서 일정을 수정한다. | 브라우저 B에 수정 결과가 반영된다. |
| TC-10 | FR-06 | 실시간 | 브라우저 A에서 일정을 삭제한다. | 브라우저 B에서도 해당 일정이 사라진다. |
| TC-11 | NFR-04 | 회귀 | 일정 기능 구현 후 채팅 메시지를 전송한다. | 채팅 메시지가 정상 전송 및 수신된다. |
| TC-12 | NFR-05 | 회귀 | 일정 기능 구현 후 칸반 태스크를 이동한다. | 태스크 상태 변경이 정상 반영된다. |
| TC-13 | NFR-06 | 코드 리뷰 | 일정 관련 코드 위치를 확인한다. | 일정 UI와 데이터 로직이 별도 컴포넌트 또는 hook으로 분리되어 있다. |
| TC-14 | NFR-07 | 정적 검사 | `npm run lint`를 실행한다. | 오류 없이 완료된다. |
| TC-15 | NFR-07 | 빌드 | `npm run build`를 실행한다. | 빌드가 성공한다. |

## 6. 결함 기록 방식

테스트 중 결함이 발견되면 다음 형식으로 GitHub Issue 또는 테스트 결과 문서에 기록한다.

| 항목 | 내용 |
|---|---|
| 결함 ID | BUG-01 |
| 발견 테스트 | TC ID |
| 현상 | 실제 발생한 문제 |
| 기대 결과 | 요구사항상 기대한 동작 |
| 원인 분석 | 확인된 원인 |
| 수정 방법 | 적용한 수정 |
| 재테스트 결과 | 통과 또는 실패 |

## 7. 인수 기준

다음 조건을 만족하면 일정 관리 기능 개선을 완료한 것으로 판단한다.

- TC-01부터 TC-13까지 필수 테스트가 통과한다.
- lint와 build 검사가 통과한다.
- 일정 생성, 수정, 삭제가 Supabase에 반영된다.
- 동일 방에 접속한 두 브라우저에서 일정 변경이 실시간 반영된다.
- 다른 방의 일정 데이터가 섞이지 않는다.
- 기존 채팅과 칸반 기능이 정상 동작한다.
- 테스트 결과와 화면 캡처가 GitHub에 기록된다.

## 8. 프로세스 적용의 교훈

기존 바이브코딩 방식에서는 기능이 화면에 나타나고 일부 동작이 가능하면 개발이 완료된 것으로 판단하기 쉬웠다. 그러나 테스트 계획을 먼저 작성하면서, 기능 구현 전에 검증해야 할 기준을 명확히 설정할 수 있었다.

특히 일정 기능은 단순히 화면에 추가되는 것이 아니라, 데이터 저장, 방별 분리, 실시간 반영, 입력 검증, 기존 기능 회귀 여부까지 확인해야 완성된 기능이라고 볼 수 있다. 따라서 테스트 계획은 AI가 생성한 코드를 검증하는 기준이자, 요구사항이 실제 제품 품질로 이어지는지를 확인하는 도구로 활용될 수 있다.
