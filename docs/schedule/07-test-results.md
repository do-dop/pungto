# Pungto 일정 관리 기능 테스트 결과

## 1. 테스트 목적

본 문서는 Pungto 일정 관리 기능이 요구사항과 테스트 계획을 만족하는지 확인한 결과를 기록한다.

초기 Pungto 개발에서는 기능이 화면에 표시되는지 중심으로 확인했지만, 이번 개선에서는 요구사항 명세서와 테스트 계획을 기준으로 기능, 예외, 통합, 실시간 동기화, 회귀 테스트, 정적 검사 및 빌드 검사를 수행하였다.

## 4. 발견한 문제와 수정 내역

### BUG-01. 일정 목록을 불러오지 못하는 문제

* 현상: 일정 탭 진입 시 “일정 목록을 불러오지 못했습니다.” 메시지가 표시됨
* 원인: Supabase에 `schedules` 테이블이 없거나 RLS policy 또는 Realtime 설정이 누락됨
* 수정: `docs/sql/create-room-access.sql`에 방 참여자 접근 제어를, `docs/sql/create-schedules-table.sql`에 일정 테이블, color 컬럼, RLS policy, Realtime publication 설정 SQL을 분리하여 추가
* 결과: SQL 실행 후 일정 조회 및 생성 가능

### BUG-02. 삭제 후 새로고침해야 화면에서 사라지는 문제

* 현상: 일정 삭제 후 현재 화면에서 바로 제거되지 않고 새로고침 후 반영됨
* 원인: 삭제 후 로컬 상태를 갱신하지 않고 Realtime 이벤트에만 의존함
* 수정: `deleteSchedule()` 성공 시 로컬 `schedules` 상태에서 해당 일정을 즉시 제거하도록 수정
* 결과: 삭제 후 새로고침 없이 현재 화면에서 제거됨

### BUG-03. 다른 브라우저에서 삭제 이벤트가 즉시 반영되지 않는 문제

* 현상: A 브라우저에서 일정을 삭제했을 때 B 브라우저에서 새로고침 전까지 일정이 남아 있음
* 원인: Supabase Realtime의 DELETE 이벤트에서 삭제된 row의 이전 데이터가 충분히 전달되지 않음
* 수정: `alter table schedules replica identity full;` 설정을 추가하고, DELETE 이벤트에서 `payload.old.id`를 기준으로 로컬 상태를 갱신하도록 수정
* 결과: 같은 방에 접속한 다른 브라우저에서도 삭제가 새로고침 없이 반영됨

## 5. 테스트 결과 요약

일정 관리 기능은 요구사항에 따라 생성, 조회, 수정, 삭제가 가능하도록 구현되었다. 기존 달력 디자인을 유지하면서 날짜 클릭을 통한 일정 추가, 색상 선택, 현재 사용자 화면 즉시 반영, 다른 브라우저 Realtime 동기화까지 확인하였다.

추가로 방 제목과 비밀번호 기반 방 생성, 비밀번호 검증 입장, 방 멤버 기반 RLS 접근 제어를 확인하였다. 일정 품질 개선 항목으로는 42칸 달력 렌더링, 일정 모달 접근성, Google Font 제거 후 빌드 안정성을 검증하였다.

정적 검사와 빌드 검사는 모두 통과하였다. 또한 기능별 구조 분리 이후 채팅, 칸반, 대시보드 회귀 테스트를 수행하여 기존 협업 기능이 정상 동작함을 확인하였다.

---

## 6. 테스트 단계의 교훈

기존 바이브코딩 방식에서는 기능이 화면에 표시되고 버튼이 동작하면 구현이 완료되었다고 판단하기 쉬웠다. 그러나 테스트 계획을 기준으로 확인한 결과, 일정 삭제 후 현재 화면이 즉시 갱신되지 않는 문제, 다른 브라우저에서 DELETE 이벤트가 반영되지 않는 문제처럼 단순 화면 확인만으로는 놓칠 수 있는 결함을 발견할 수 있었다.

또한 기존 달력 기반 사용 흐름을 유지한 상태에서 실제 데이터 저장과 실시간 동기화를 연결함으로써, 기능 구현과 사용자 경험을 함께 고려해야 함을 확인하였다.
