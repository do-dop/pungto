# Pungto 일정 관리 기능 유스케이스 명세

## 1. 목적

본 문서는 Pungto의 목업 상태 일정 기능을 실제 실시간 일정 관리 기능으로 개선하기 위해 주요 사용 사례를 정의한다.

기존 Pungto는 채팅, 칸반, 대시보드 등 일부 기능은 실제 데이터 저장 및 실시간 동기화가 적용되어 있었지만, 일정 기능은 화면 중심의 목업 기능에 가까웠다. 따라서 이번 개선에서는 일정 조회, 생성, 수정, 삭제, 실시간 반영 흐름을 명확히 정의하고 이를 구현 및 테스트 기준으로 활용한다.

---

## 2. 액터 정의

| 액터 | 설명 |
|---|---|
| 방 참여자 | 닉네임과 브라우저 세션 ID를 기반으로 Pungto 협업방에 입장한 사용자 |
| Supabase | 일정 데이터를 저장하고 Realtime 이벤트를 전달하는 외부 데이터 저장 및 동기화 시스템 |

## 3. 유스케이스 목록

| ID | 유스케이스 | 주 액터 | 설명 |
|---|---|---|---|
| UC-01 | 일정 목록 조회 | 방 참여자 | 현재 방에 등록된 일정을 확인한다. |
| UC-02 | 일정 생성 | 방 참여자 | 제목, 날짜, 설명을 입력하여 새 일정을 등록한다. |
| UC-03 | 일정 수정 | 방 참여자 | 기존 일정의 제목, 날짜, 설명을 변경한다. |
| UC-04 | 일정 삭제 | 방 참여자 | 불필요한 일정을 삭제한다. |
| UC-05 | 일정 변경 실시간 수신 | 방 참여자, Supabase | 다른 사용자의 일정 변경 사항을 새로고침 없이 확인한다. |

## 4. 핵심 유스케이스 명세: UC-02 일정 생성

| 항목 | 내용 |
|---|---|
| 유스케이스명 | 일정 생성 |
| 주 액터 | 방 참여자 |
| 관련 요구사항 | FR-02, FR-05, FR-06, NFR-01, NFR-02 |
| 사전 조건 | 사용자가 유효한 room ID의 협업방에 입장해 있어야 한다. |
| 사후 조건 | 새 일정이 현재 방 기준으로 저장되고, 같은 방 참여자 화면에 반영된다. |

### 기본 흐름

1. 사용자가 방 화면에서 일정 메뉴를 선택한다.
2. 시스템은 현재 room ID에 해당하는 일정 목록을 표시한다.
3. 사용자가 일정 추가 버튼을 선택한다.
4. 시스템은 일정 입력 화면을 표시한다.
5. 사용자는 제목, 날짜, 설명을 입력한다.
6. 사용자가 저장 버튼을 선택한다.
7. 시스템은 제목과 날짜가 입력되었는지 검증한다.
8. 시스템은 일정을 현재 room ID와 연결하여 Supabase에 저장한다.
9. 시스템은 저장된 일정을 현재 사용자 화면에 표시한다.
10. Supabase Realtime 이벤트를 통해 같은 방의 다른 참여자 화면에도 일정이 반영된다.

### 대안 흐름 A1. 제목 미입력

1. 사용자가 제목을 입력하지 않고 저장을 선택한다.
2. 시스템은 저장을 수행하지 않는다.
3. 시스템은 제목 입력이 필요하다는 안내를 표시한다.
4. 사용자는 입력 화면에서 제목을 다시 입력할 수 있다.

### 대안 흐름 A2. 날짜 미입력

1. 사용자가 날짜를 입력하지 않고 저장을 선택한다.
2. 시스템은 저장을 수행하지 않는다.
3. 시스템은 날짜 입력이 필요하다는 안내를 표시한다.
4. 사용자는 입력 화면에서 날짜를 다시 입력할 수 있다.

### 예외 흐름 E1. 저장 실패

1. Supabase 저장 요청이 실패한다.
2. 시스템은 저장 실패 메시지를 표시한다.
3. 기존 일정 목록 상태는 유지한다.
4. 사용자는 다시 저장을 시도할 수 있다.

## 5. 핵심 유스케이스 명세: UC-03 일정 수정

| 항목 | 내용 |
|---|---|
| 유스케이스명 | 일정 수정 |
| 주 액터 | 방 참여자 |
| 관련 요구사항 | FR-03, FR-05, FR-06, NFR-01, NFR-02 |
| 사전 조건 | 수정할 일정이 현재 방에 존재해야 한다. |
| 사후 조건 | 수정된 일정 정보가 저장되고 같은 방 참여자 화면에 반영된다. |

### 기본 흐름

1. 사용자가 일정 목록에서 수정할 일정을 선택한다.
2. 시스템은 기존 일정 정보를 입력 화면에 표시한다.
3. 사용자가 제목, 날짜, 설명을 수정한다.
4. 사용자가 저장 버튼을 선택한다.
5. 시스템은 필수 입력값을 검증한다.
6. 시스템은 해당 일정을 Supabase에서 수정한다.
7. 수정 결과가 현재 사용자 화면에 표시된다.
8. 같은 방의 다른 참여자 화면에도 수정 결과가 실시간 반영된다.

## 6. 핵심 유스케이스 명세: UC-04 일정 삭제

| 항목 | 내용 |
|---|---|
| 유스케이스명 | 일정 삭제 |
| 주 액터 | 방 참여자 |
| 관련 요구사항 | FR-04, FR-06, FR-07 |
| 사전 조건 | 삭제할 일정이 현재 방에 존재해야 한다. |
| 사후 조건 | 삭제된 일정이 목록에서 제거되고 같은 방 참여자 화면에서도 사라진다. |

### 기본 흐름

1. 사용자가 일정 목록에서 삭제할 일정을 선택한다.
2. 시스템은 삭제 확인 메시지를 표시한다.
3. 사용자가 삭제를 확인한다.
4. 시스템은 해당 일정을 Supabase에서 삭제한다.
5. 삭제된 일정은 현재 사용자 화면에서 제거된다.
6. 같은 방의 다른 참여자 화면에서도 해당 일정이 제거된다.

### 대안 흐름 A1. 삭제 취소

1. 사용자가 삭제 확인 단계에서 취소를 선택한다.
2. 시스템은 삭제를 수행하지 않는다.
3. 기존 일정 목록을 유지한다.

---

## 7. 프로세스 적용의 교훈

초기 Pungto 개발에서는 화면을 먼저 생성한 뒤 동작을 확인하는 방식으로 진행되어, 일정 기능이 실제 협업 기능으로 완성되었는지 판단하기 어려웠다.

유스케이스 명세를 작성하면서 사용자 동작, 시스템 응답, 예외 흐름, 사후 조건을 명확히 구분할 수 있었다. 이를 통해 AI에게 구현을 요청하기 전에도 기능의 정상 흐름과 오류 흐름을 구체적으로 전달할 수 있게 되었고, 이후 테스트 케이스를 작성하는 기준도 명확해졌다.
